# 🤝 tof-duo — 3개의 ToF 센서로 공간을 넓게 감시 (Arduino UNO Q + MQTT)

VL53L8CX 8x8 ToF 센서 3개(보드 3대)의 값을 **MQTT 브로커(인터넷)** 로 주고받아, 한 화면에서 동시에 보고
**사람이 센서 영역에 들어왔는지, 몇 명인지, 가까이 모였는지(동시 접근), 과하게 움직이는지(움직임 경보)** 를 감시하는 Arduino App.

| 기능 | 설명 |
|---|---|
| 히트맵 공유 | 세 보드의 8x8 거리값을 실시간으로 한 화면에 (보드 웹 UI, 노트북 Chrome 허브) |
| 파노라마 레이더 | 센서 3개를 부채꼴로 세워 약 130° 시야, 사람 위치/인원/추적(센서 경계를 넘어도 같은 ID), 체류 히트맵 |
| 동시 접근 알림 | 둘 이상의 센서가 400mm 이내를 감지하면 경고 |
| 움직임 경보 | 센서별 평균 움직임이 기준(기본 40mm)을 넘으면 경고 배너/테두리/경보음 |
| 링크 대시보드 | 팀원별 연결 상태, Hz, 손실률, 지연, 센서가 멈추면 `응답 없음` |
| 안정화 | 튐 보정(3프레임 중간값), 빈칸 채움, 센서 자동 복구, 설정 저장 |

> **팀원에게**: 이 README를 처음부터 끝까지 AI(Claude 등)에게 붙여 넣고
> "이 README처럼 내 UNO Q에 구현해줘. 내 보드 ID는 ___, 이름은 ___, 팀 코드는 ___ 야"라고 하면 됩니다.
> 구현 방식이 달라도 **4. 통신 규약**만 지키면 서로 연동됩니다.

## 빠른 시작 (GitHub에서 받아 바로 실행)

**준비물**: UNO Q 1대 + VL53L8CX 1개(배선은 3장), 보드가 **인터넷이 되는 와이파이**에 연결된 상태, 노트북 Chrome.

1. **보드에 코드 넣기** (택1)
   - 보드에 git이 있으면(UNO Q에는 기본 설치): 저장소를 받고, **`app.yaml`이 들어 있는 폴더**를 `~/ArduinoApps/tof-duo`로 복사한다.
     ```bash
     cd ~ && git clone https://github.com/jinse12/tof-duo.git tof-duo-repo
     cp -r tof-duo-repo/tof-duo ~/ArduinoApps/tof-duo     # 저장소 안의 tof-duo/ 폴더가 앱 폴더
     ```
     (저장소 루트에 바로 `app.yaml`이 보이면 `cp -r tof-duo-repo ~/ArduinoApps/tof-duo` 로 복사)
   - 또는 앱 폴더를 zip으로 만들어 `arduino-app-cli app import <zip 경로>` (또는 App Lab의 가져오기).
2. **시작**
   ```bash
   arduino-app-cli app start ~/ArduinoApps/tof-duo
   ```
   첫 실행은 스케치 컴파일/업로드, 라이브러리 설치, 센서 초기화 때문에 **1~3분** 걸린다. 이미 다른 앱이 실행 중이면 그 앱이 중지된다.
3. **내 보드 설정**: 브라우저에서 `http://<보드 IP>:7000` 접속 -> **팀 코드**(전원 동일), **보드 ID**(`tof1`/`tof2`/`tof3`, 서로 다르게), **내 이름**(한글 가능)을 입력하고 **연결**.
   설정은 보드의 `data/config.json`에 저장되어 앱을 재시작해도 유지된다 (이 파일은 git에 올라가지 않는다).
4. **허브 열기** (3개를 한 화면에서 + 레이더)
   - 같은 네트워크: `http://<보드 IP>:7000/hub/index.html?team=<팀 코드>` 또는 보드 웹 UI 상단의 **📡 레이더 / 허브 열기** 버튼
   - 어느 네트워크든: 저장소의 `assets/hub/index.html` 파일을 노트북 Chrome으로 열고 팀 코드를 입력 (인터넷만 되면 됨)
5. 팀원이 켜지면 패널이 자동으로 추가된다. 상단 탭에서 **2D 히트맵 / 3D 포인트 클라우드 / 📡 레이더**를 고른다.

안 될 때는 **7-3. 문제 해결**을 본다.

## 0. 왜 MQTT인가 (HTTP POST에서 바꾼 이유)

처음에는 보드끼리 `POST http://<상대IP>:7000/peer`로 직접 보냈습니다.
하지만 팀원마다 **와이파이(네트워크)가 달라** 사설 IP(192.168.x.x)로는 서로 닿지 못합니다.
그래서 **모두가 인터넷상의 같은 브로커에 접속**하는 방식(publish/subscribe)으로 바꿨습니다.

- 보드는 브로커로 "나가는" 연결만 하므로 공유기/NAT/클라이언트 격리와 무관합니다.
- 서로의 IP를 몰라도 되고, 같은 **팀 코드**만 쓰면 자동으로 서로 보입니다. 인원 수 제한이 없습니다.
- 노트북 Chrome이 같은 토픽을 구독하면 "허브" 화면도 만들 수 있습니다 (7장 참고).

## 1. 전체 구조

```
VL53L8CX --I2C--> sketch.ino (MCU, 15Hz, 노이즈 필터)
                     | Bridge.notify("tof_zones", 64값)
                     v
                  main.py (Docker 컨테이너)
                     |-- ui.send_message("local_zones") --> 내 브라우저 (내 히트맵)
                     |-- MQTT publish  tofduo/<팀>/<이름>/frame  ---->  [브로커]
                     |<- MQTT subscribe tofduo/<팀>/+/frame  <----------  (다른 팀원들)
                     '-- ui.send_message("peer_zones") --> 내 브라우저 (팀원 히트맵들)
```

- MCU는 센서 읽기/필터만, 네트워크와 웹은 전부 Python(컨테이너)이 처리합니다.
- 별도 서버 없이 `arduino:web_ui` Brick + `paho-mqtt`(컨테이너에 이미 설치됨)만 사용합니다.

## 3. 하드웨어

| 센서 | UNO Q |
|---|---|
| VCC | 3.3V |
| GND | GND |
| SDA / SCL | **보드의 전용 SCL/SDA 헤더** (코드의 `Wire`) |
| LPn | D7 |

UNO Q에는 I2C 버스가 3개 있고 코드 이름이 다릅니다. **꽂은 위치와 코드의 `Wire`가 일치해야 합니다.**

| 코드 | 위치 |
|---|---|
| `Wire` | 전용 SCL/SDA 2핀 헤더 (이 프로젝트 기본) |
| `Wire1` | Qwiic 커넥터 |
| `Wire2` | A4(SDA) / A5(SCL) |

센서를 다른 곳에 꽂았다면 `sketch.ino`의 `VL53L8CX sensor_tof(&Wire, LPN_PIN);`과
`Wire.begin()`/`Wire.setClock()`의 `Wire`를 같이 바꾸세요.

## 4. 통신 규약 (팀원과 반드시 맞춰야 하는 부분)

### 4.1 브로커

| 항목 | 값 |
|---|---|
| 호스트 | `broker.hivemq.com` (공용, 인증 없음. UI에서 바꿀 수 있음) |
| 포트 | `1883` (TCP, 평문) |
| 프로토콜 | MQTT 3.1.1/5 (paho-mqtt 2.x 사용) |

공용 브로커는 **토픽만 알면 누구나 구독**할 수 있습니다. 거리값이라 민감하진 않지만,
**팀 코드는 추측하기 어려운 문자열**로 정하세요. 코드/README에 실제 팀 코드를 커밋하지 마세요
(아래 `<팀코드>`는 자리표시자입니다).

### 4.2 토픽

`<team>` = 팀 코드, `<name>` = 보드(사람) 이름. 둘 다 영문/숫자/`_`/`-`만 허용 (최대 24자). **이름은 팀 안에서 유일해야 합니다.**

| 토픽 | 방향 | QoS/retain | 내용 |
|---|---|---|---|
| `tofduo/<team>/<name>/frame` | 보드 -> 브로커 | QoS0 | 센서 프레임 (JSON, 아래) |
| `tofduo/<team>/<name>/status` | 보드 -> 브로커 | QoS1, retain | `"online"` / `"offline"` (끊기면 브로커가 `offline`을 발행: Last Will) |
| `tofduo/<team>/<name>/cmd` | 허브 -> 보드 | QoS0 | 보드로 보내는 명령 (확장용, 현재는 웹 UI에 `cmd` 이벤트로만 전달) |

각 보드는 `tofduo/<team>/+/frame`, `tofduo/<team>/+/status`, `tofduo/<team>/<내이름>/cmd`를 구독하고,
**자기 이름의 메시지는 무시**합니다.

### 4.3 frame 페이로드

```json
{
  "zones": [/* 정수 64개, 8x8을 행 우선(row-major), 단위 mm, 0 = 측정 없음 */],
  "seq": 123,
  "ts": 1731470000000,
  "name": "tof1",
  "label": "진세"
}
```

- `zones` 길이는 반드시 64. 아니면 수신 측이 버립니다.
- `seq`: 보낼 때마다 +1. 수신 측이 빠진 번호로 **패킷 손실률**을 계산합니다.
- `ts`: 보낸 시각(epoch ms). 보드마다 시계가 달라서 지연 측정에는 신뢰하지 마세요.
- `name`은 토픽에 쓰는 **보드 ID**(영문/숫자). `label`은 화면에 보여 줄 **본인 이름**(한글 가능, 선택, 최대 24자). 화면은 `label`이 있으면 그것을, 없으면 `name`을 표시한다.
- 발행 주기는 **10Hz**.

### 4.4 이 앱의 HTTP API (자기 보드 웹 UI용)

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/set_config` | `{"team","name","label?","broker?","port?"}` 로 설정하고 MQTT 재접속. team/name 필수, label은 화면 표시 이름 |
| POST | `/reset` | 받은 프레임/팀원 목록/카운터를 모두 지움 (화면의 `프레임 초기화` 버튼이 호출) |
| GET | `/state` | 현재 설정 `{broker, port, team, name}` |

### 4.5 브라우저로 가는 WebSocket 메시지 (서버 -> 브라우저)

| 이름 | 내용 | 주기 |
|---|---|---|
| `local_zones` | `{zones:[64]}` 내 센서 | 센서 갱신마다 (~15Hz) |
| `peer_zones` | `{name, label, zones:[64]}` 팀원 센서 | 수신할 때마다 |
| `status` | `{team,name,label,broker,mqtt,tx_ok,peers:[{name,label,alive,fps,loss_pct,age_ms}]}` | 1Hz |
| `cmd` | `{payload}` 허브가 보낸 명령 | 수신할 때 |

### 4.6 Bridge 이름 (MCU <-> Python)

- sketch: `Bridge.notify("tof_zones", std::array<int16_t,64>)`, `Bridge.notify("tof_min_distance", float)`
- python: `Bridge.provide("tof_zones", ...)`, `Bridge.provide("tof_min_distance", ...)`
- 이름이 한 글자라도 다르면 **에러 없이 조용히 실패**합니다.

## 5. 구현 포인트와 함정 (실제로 겪은 것들)

| 주제 | 내용 |
|---|---|
| I2C 위치 | 코드가 `Wire2`(A4/A5)인데 센서를 전용 SCL/SDA 헤더에 꽂아서 값이 안 올라왔음 -> 꽂은 곳과 `Wire`/`Wire1`/`Wire2`를 일치시킬 것 |
| 갱신 속도 | `set_ranging_frequency_hz()`를 안 부르면 센서 기본값 **1Hz**. `start_ranging()` 전에 15를 설정. `delay()`는 폴링 주기일 뿐 |
| 8x8 최대 속도 | 8x8은 최대 15Hz, 4x4는 최대 60Hz |
| Bridge 배열 | C 배열은 컴파일 에러. `#include <array>` 후 `std::array<int16_t,64>` 사용 |
| 값이 빈다/튄다 | 낮은 신뢰도 존을 바로 0으로 만들면 빈칸이 늘어남. 현재는 `status==255`/거리 0만 제외하고, 끊긴 존은 **마지막 값을 8프레임(약 0.5초) 유지**. 정상 값은 평균(EMA α=0.5), 250mm 이상 변하면 실제 움직임으로 보고 즉시 추종 |
| 측정 한계 | 검은색/투명/거울 표면, 강한 햇빛, 3~4m 이상은 원래 측정이 안 됨 |
| 센서 초기화 | 앱을 연속으로 재시작하면 센서 프레임이 몇 분간 안 올라올 때가 있었음(원인 미확인). 안 오면 앱을 한 번 더 재시작 |
| MQTT 스레드 | `loop_start()`로 paho 백그라운드 스레드 사용. 공유 상태는 `Lock`으로 보호. 끊기면 `reconnect_delay_set(1,10)`으로 자동 재접속 |
| 자기 메시지 | 같은 팀 토픽을 구독하므로 자기 프레임도 돌아옴 -> 이름이 같으면 무시 |
| `App.run()` | 파일 맨 끝에 한 번. 그 뒤 코드는 실행되지 않음 |
| 시리얼 모니터 | 시작 메시지는 init 때 한 번뿐이라 늦게 붙이면 안 보임. 동작 확인은 `app logs` |
| 포트 | 7000은 web_ui가 자동 노출 (`app.yaml`의 `ports` 불필요) |

## 6. 실행과 연결

```bash
arduino-app-cli app start ~/ArduinoApps/tof-duo
arduino-app-cli app logs  ~/ArduinoApps/tof-duo --follow
```

1. 브라우저에서 `http://<내 보드 IP>:7000` 접속 (보드와 같은 네트워크의 PC/폰)
2. **팀 코드**(팀 전원이 동일), **내 이름**(전원이 서로 다르게)을 입력하고 **연결**
3. 상단이 `broker.hivemq.com 연결됨`으로 바뀌고, 팀원이 켜지면 히트맵 패널이 자동으로 추가됨
4. 팀원이 꺼지면 해당 패널이 `응답 없음`으로 표시되고, 다시 켜지면 자동 복구

환경변수 `TEAM_CODE`, `BOARD_NAME`, `MQTT_BROKER`, `MQTT_PORT`로 초기값을 줄 수도 있습니다.

### 화면 기능
- 보기: 행렬(8x8 칸 분리) / 부드럽게(보간), mm 숫자 토글
- 둘 이상이 400mm 이내로 가까워지면 "동시 접근" 배너
- 팀원별 연결 상태, 수신 Hz, 손실률

## 7. 강의실(다른 네트워크) 사용 체크리스트

1. **보드 와이파이**: 보드에는 이전 장소의 와이파이가 저장돼 있음. 새 장소의 와이파이를 App Lab/adb로 다시 설정.
   학교 와이파이가 로그인 페이지나 계정 인증(802.1X)을 요구하면 보드가 붙지 못할 수 있음.
2. **포트**: 학교 네트워크가 브로커 1883 포트를 막을 수 있음 (특히 학교 PC). 막히면 아래 대안 사용.
3. **대안**: 한 명의 **휴대폰 핫스팟**에 보드/노트북을 모두 연결하면 이 제약이 모두 사라짐.
4. 모두 같은 **팀 코드**, 서로 다른 **이름**인지 화면 상단과 `팀 코드` 칸에서 확인.

## 7-1. 팀 구성 (보드 이름 규칙)

토픽의 `<name>`은 영문이어야 해서 **아래 ID를 보드 이름으로 쓴다.** 허브가 ID를 사람 이름으로 바꿔 보여준다.

| 보드 이름 (토픽/연결 화면에 입력) | 사람 |
|---|---|
| `tof1` | 진세 |
| `tof2` | 혜연 |
| `tof3` | 연우 |

표시 이름은 `assets/hub/index.html` 맨 위 `LABELS`에서 바꾼다. 팀 코드는 전원이 같은 값, 이름은 서로 달라야 한다.

## 7-2. 허브 (노트북 Chrome) — 구현 완료

`assets/hub/index.html` 한 파일. **서버 없이** Chrome에서 열면 브로커의 WebSocket에 직접 붙어 `tofduo/<team>/+/frame`을 구독한다.
인터넷만 되면 되고 보드와 같은 네트워크일 필요가 없다. (CDN에서 mqtt.js, three.js를 불러오므로 인터넷 필요)

사용법:
1. `hub/index.html`을 Chrome으로 연다 (파일 더블클릭, 또는 보드가 켜져 있으면 `http://<보드IP>:7000/hub/index.html`)
2. 팀 코드 입력 후 **연결**. 또는 주소 끝에 `?team=<팀코드>`를 붙이면 자동 연결.
3. 기본 접속 주소는 `ws://broker.hivemq.com:8000/mqtt`. https 페이지에서는 `wss://broker.hivemq.com:8884/mqtt`.

기능:
- 보드별 히트맵 패널 자동 생성 (연결 상태, Hz, 손실률, 최소 거리)
- 랭킹: 지금 가장 가까운 사람(🥇), 활동량 가장 큰 사람(🔥)
- 둘 이상이 400mm 이내면 "동시 접근" 배너
- 최소 거리 추이 그래프 (최근 2분, 보드별 색)
- 보기 전환: 2D 히트맵 / **3D 포인트 클라우드** (센서 3개를 한 장면에, 마우스로 회전/확대)

3D 좌표 변환: 8x8 존 `i` 의 열 `c=i%8`, 행 `r=i/8` 에 대해 각도 `(c-3.5)*45/8 도`, `(r-3.5)*45/8 도` (센서 시야 45°x45°),
`x=d*tan(ax)`, `y=-d*tan(ay)`, `z=-d` (d = 거리 mm). 센서마다 x 방향으로 1800mm씩 띄워서 나란히 배치.

아직 구현하지 않은 것: 허브 -> 보드로 명령 보내기(LED 매트릭스 표시). 보드는 `cmd` 토픽을 받아 웹 UI로 전달만 한다.


### 화면 배치 (전체화면 권장)
- 화면 크기에 맞춰 비율을 유지하며 선명하게 그린다(devicePixelRatio 반영). 큰 모니터에서도 늘어나거나 흐려지지 않는다.
- **레이더 탭**은 넓은 화면(가로 1000px 이상)에서 레이더를 왼쪽에 크게, 히트맵 3개를 오른쪽에 세로로 쌓아 **한 화면에 들어오게** 한다. 이때 작은 히트맵은 색만 보이고 mm 숫자는 2D 탭에서 본다.
- 1366x768 같은 작은 노트북에서는 세로가 모자라 스크롤된다. 영상을 찍을 때는 Chrome 전체화면(F11), 1920x1080을 권장한다.

### 튐 보정 / 큰 움직임 구간 / 히트맵 보기 (허브)
- **튐 보정**(체크박스): 한 프레임만 120mm 넘게 튀는 존 값을 최근 3프레임 중간값으로 바꾼다. 이웃 존 2개 이상이 같은 방향으로 함께 변하면 실제 움직임으로 보고 그대로 둔다. 짧은 측정 끊김(0)은 마지막 값을 유지.
- **큰 움직임 구간**: 프레임 간 평균 변화가 60mm를 넘으면 구간 시작, 1초 잠잠하면 종료. 센서별 마지막 구간의 시각/길이/최대 변화/보정 개수를 표시하고 그래프에 색으로 칠한다. (가짜 튐 값 3%를 섞은 시뮬레이션에서 보정을 끄면 3개 센서가 계속 "진행 중"이었고, 켜면 실제 움직임 구간만 기록됨. 실제 센서에서 임계값이 맞는지는 확인 전)
- **히트맵 보기**: `8x8 칸`(칸마다 mm 숫자) / `8x8 부드럽게`(64x64 쌍선형 보간). **빈칸 채움**은 측정 안 된 칸을 주변 값의 중간값으로 추정해 흐리게(기울임체 숫자) 표시한다 (화면 표시만 바꾸고 원본 값은 그대로).
- 캔버스는 항상 정사각형(최대 300px)으로 그린다. 배율 1배에서 높이가 갱신되지 않아 8행 중 4행만 보이던 버그를 수정함 (`fitCanvas`).

### 움직임 과다 경보 (허브)
- 센서별 **평균 움직임**(프레임 간 변화의 약 1초 평균, mm)이 기준값을 넘으면 노란 경고줄 `⚠ 움직임 과다 · 이름 80mm`, 그 패널 테두리 주황색, (체크 시) 경보음.
- 상단 **움직임 경보** 칸에서 기준값(기본 40mm)을 바꾼다. 켜진 뒤에는 기준값의 60% 아래로 내려가야 꺼진다 (깜빡임 방지).
- 센서 상태를 직접 넣어서 켜짐/꺼짐/히스테리시스를 확인했다. 실제 사람 움직임에서 40mm가 적당한지는 현장에서 조정해야 한다.

### 설정 저장
`POST /set_config` 가 성공하면 `data/config.json`에 저장하고, 앱이 시작될 때 읽는다 (저장값 > 환경변수 > 기본값). 재시작해도 팀 코드/ID/이름을 다시 입력하지 않아도 된다.

### 레이더 보기 (3-센서 파노라마) — 책상 위 부채꼴 배치

센서 3개를 **한 책상에 모아** 서로 다른 각도로 세우고, 앞을 지나가는 사람을 위에서 본 평면도에 점으로 표시한다.
점퍼 길이 때문에 센서를 멀리 둘 수 없을 때 쓰는 구성이다. 추가 하드웨어(서보, 자이로) 없음.

**설치**
- 센서를 책상 앞쪽에 나란히 두고 `tof1`=왼쪽(-40°), `tof2`=가운데(0°), `tof3`=오른쪽(+40°)으로 **바깥쪽으로 돌려서** 놓는다 (골판지 쐐기/각도기로 맞춤). 각도는 허브에서 바꿀 수 있다.
- 센서끼리 **서로 마주 보지 않게** 모두 같은 방향(앞쪽)을 보게 둔다. 한 센서의 적외선이 다른 센서의 수신부로 직접 들어가면 간섭이 생길 수 있다 (이 간섭은 실제 센서로 확인하지 못했으니 현장에서 켜고 끄며 값을 비교할 것).
- 센서 높이는 사람 몸통 높이(약 1m) 권장. 유효 거리는 약 3m.
- 센서 하나의 시야는 가로 45°, 3개를 40° 간격으로 두면 약 130°이고 경계에서 약 5°씩 겹친다.

**사용 순서**
1. 허브 `보기`를 **레이더 (3센서 파노라마)** 로 바꾼다 (또는 주소에 `&mode=radar`).
2. 앞이 **빈 상태**에서 **배경 학습**(3초)을 누른다. 존별 배경 거리의 중간값을 저장한다.
3. 배경보다 200mm 이상 가까워진 존을 "사람"으로 본다. 한 열에서 2개 이상 존이 가까워지면 그 열의 거리(중간값)와 각도로 (x, y)를 만든다.
4. 400mm 이내의 점들을 한 사람으로 묶고(클러스터링), 프레임마다 가장 가까운 기존 트랙에 이어 붙여 **ID를 유지**한다 (센서 경계를 넘어도 같은 ID). 3초간 안 보이면 트랙 삭제.
5. 화면 하단에 현재 인원, 지나간 사람 수(1초 이상 유지된 ID)를 표시한다.

**모드**
- **부채꼴(넓게)**: 위 설명대로 3개 시야를 이어 붙임.
- **겹치기 (median-of-3)**: 3개를 같은 방향으로 겹쳐 놓았을 때 쓴다. 존별 중간값(유효값이 2개면 평균)으로 합성해서 튀는 값/빈칸을 줄인다. 합성 히트맵이 패널로 추가된다.
- **좌우 반전** 체크: 실제 센서의 열 방향이 화면과 반대로 보일 때 쓴다 (센서 방향에 따라 달라질 수 있어 실제 장비로 확인 필요).
- **체류 히트맵**: 사람이 오래 머문 자리를 주황색으로 누적 표시.

**시뮬레이션으로 확인한 것** (실제 센서 아님): 가상 센서 3개(-40°/0°/+40°, 배경 2.5m)에서 사람 A가 1.5m 앞을 왼쪽에서 오른쪽으로 걷고 사람 B가 서 있을 때,
A가 ID #1로 `tof1 -> tof1+tof2 -> tof2 -> tof2+tof3 -> tof3`를 지나는 동안 ID가 바뀌지 않았고 B는 겹침 구역에서 ID #2로 유지되어 총 ID 2개, 누적 2명으로 집계됨.
(트랙 삭제 시간이 1.5초일 때는 가려졌던 B의 ID가 바뀌어 3초로 늘림.)

**한계**
- 센서 앞 반원 반경 약 3m의 구역만 보인다. 사람이 붙어 있으면 한 명으로 합쳐질 수 있다.
- 센서 간격이 좁아서 삼각측량으로 위치 정확도를 높이는 효과는 거의 없다. 장점은 시야 확장, 경계 넘는 추적, 겹침 구역 교차 확인, 한 대가 꺼져도 계속 동작하는 점이다.
- 실제 센서에서의 오탐(바닥/책상 반사, 사람 옷 색)은 확인 전이다. 배경 학습 후 오탐이 보이면 200mm 임계값을 조정한다.

### 허브 개발 중 겪은 것
- **공용 브로커가 가끔 응답하지 않는다.** WebSocket은 열리는데 CONNACK이 안 오는 경우가 있었다(짧은 시간에 접속을 반복하면 더 심했음). 같은 요청이 몇 분 뒤 정상 동작. 안 되면 몇 초 뒤 다시 연결하거나 브로커를 바꾼다.
  다른 브로커의 WebSocket 주소(테스트에서 CONNACK 확인): `ws://broker.emqx.io:8083/mqtt`, `wss://broker.emqx.io:8084/mqtt`, `ws://test.mosquitto.org:8080/`.
  보드의 `MQTT_BROKER`/화면의 브로커 칸(TCP 1883)도 같은 브로커로 맞춰야 한다.
- 3D는 WebGL이 필요하다. 없으면 3D 영역에 안내 문구만 나오고 나머지 화면은 정상 동작.
- 시리얼 한글 폰트가 없는 환경(헤드리스 브라우저)에서는 한글이 네모로 보일 수 있음. 일반 PC는 문제없음.


### 프레임 초기화 / 이름 표시 / 시계 / 지연
- **프레임 초기화** 버튼(보드 웹 UI, 허브 둘 다): 받은 프레임, 패널, 통계(손실률, 보정 횟수), 추적, 학습한 배경을 모두 지운다. 녹화 직전에 누르면 "지금부터 들어오는 실시간 값"만 보이는 것을 증명할 수 있다. 센서가 계속 보내므로 패널은 새 프레임이 오면 다시 나타난다.
- **이름 표시**: 보드 웹 UI의 "내 이름(한글 가능)" 칸에 본인 이름을 적고 연결하면 `label`로 전송되어 모든 화면에 `tof1` 대신 그 이름이 나온다. 허브의 `LABELS`는 `label`이 없을 때만 쓰는 대체값이다.
- **시계**: 허브 상단의 `HH:MM:SS.mmm` 시계. 화면 녹화와 카메라 영상을 맞출 때 기준으로 쓴다.
- **지연 표시**: 패널의 `지연 ≈ N ms`는 `보낸 시각(ts)`과 허브가 받은 시각의 차이의 중간값이다. **보드와 노트북의 시계가 같아야 정확**하다(둘 다 인터넷 시간 동기화 필요). 같은 기기에서 시험했을 때 약 380~470ms였다 (공용 브로커 경유 왕복 포함, 센서 15Hz 측정 지연 포함).

## 7-3. 문제 해결 (실제로 겪은 것 위주)

| 증상 | 확인 | 해결 |
|---|---|---|
| 히트맵이 안 나옴 / 보드 UI에 "내 센서 데이터가 들어오지 않습니다" | `arduino-app-cli monitor` 로 시리얼 확인 | `I2C 0x29: NOT found` 또는 `NO RESPONSE`면 **배선/전원/센서 불량**. 점퍼를 다시 꽂고 VCC=3.3V, GND, SDA/SCL, LPn=D7 확인 |
| `I2C 0x29 RESPONDS`인데 `init failed`가 반복 | 시리얼 | 센서 불량 가능성. **이번 프로젝트에서 응답이 들쭉날쭉하던 센서를 다른 센서로 바꾸자 바로 해결됨**. I2C를 100kHz로 낮춰 시험해도 된다 (`Wire.setClock`) |
| 센서가 중간에 멈춤 | 시리얼 `no data for 3 s -> sensor stalled` | 스케치가 자동으로 재초기화한다. 계속 반복되면 접촉 불량 |
| 보드가 갑자기 재부팅/SSH 끊김 | `last -x reboot` | 전원 문제(USB 케이블/전원 어댑터) 의심. 정상 종료 기록 없이 부팅되면 전원 차단 |
| 허브에 팀원이 안 나옴 | 팀 코드 오타, 보드 ID 중복 | 팀 코드는 대소문자 구분. 보드 ID는 팀 안에서 유일해야 함 |
| MQTT 연결 안 됨 (`connack timeout`) | 브로커/포트 | 공용 브로커가 가끔 응답 안 함 -> 몇 초 뒤 재시도 또는 다른 브로커. 학교 네트워크가 1883을 막으면 핫스팟 |
| 레이더가 안 보임 | 어느 페이지인지 | 레이더는 **허브 페이지**(`/hub/index.html`)에만 있다. 보드 웹 UI의 `📡 레이더 / 허브 열기` 버튼 사용 |
| 첫 시작이 오래 걸림 | 앱 로그 | 스케치 컴파일 + 센서 펌웨어 업로드로 1~3분. 연속으로 재시작하면 더 늦어질 수 있음 |

## 7-4. 시연 영상 촬영 가이드

목표: (1) 세 보드가 같은 팀 코드로 MQTT를 통해 실시간으로 주고받는 것, (2) 실제 움직임과 Chrome 화면의 값이 일치하는 것을 한 영상에 보여 준다.

**권장 구성: 한 번에 녹화 (OBS Studio, 무료)**
- 장면 하나에 소스 두 개를 둔다: ① 화면 캡처(허브가 열린 Chrome) ② 영상 장치(노트북 웹캠 또는 폰 카메라). 왼쪽에 실제 장면(센서 앞에서 손/사람이 움직이는 모습과 보드), 오른쪽에 허브를 배치한다.
- 한 파일로 녹화되므로 **영상과 화면이 자동으로 같은 시간축**에 있다. 별도 동기화 작업이 필요 없다.
- 폰 카메라를 쓰려면 OBS에 폰을 웹캠으로 연결(Camo, DroidCam 등)하거나, 폰은 별도로 찍고 아래 "따로 찍을 때"를 따른다.

**따로 찍을 때 (폰은 폰대로, 화면 녹화는 따로)**
- 시작할 때 폰으로 **허브 화면의 시계**(`HH:MM:SS.mmm`)가 보이게 한 번 찍고, 박수를 한 번 친다. 편집에서 그 순간을 맞춘다.
- 화면 녹화는 OBS 또는 Windows `Win+Alt+R` / macOS `Shift+Cmd+5`.

**촬영 전 준비**
1. 세 보드가 같은 **팀 코드**, 서로 다른 **보드 ID**(`tof1`/`tof2`/`tof3`), 각자 **본인 이름**(label)을 입력했는지 확인한다.
2. 허브를 Chrome 전체화면(F11)에서 100% 배율로 연다. 북마크 바, 알림은 끈다. 해상도 1920x1080, 30fps.
3. 녹화 직전에 **프레임 초기화**를 눌러, 영상 속 값이 모두 그 뒤에 들어온 실시간 값임을 보이게 한다.
4. 와이파이/핫스팟 연결과 브로커 접속(허브 우측 상단 "브로커 연결됨")을 확인한다.

**촬영 순서 (약 2분)**
1. 허브 전체: 세 이름의 패널, 각 패널의 `Hz / 손실 / 지연`, 상단 시계.
2. **진세** 센서 앞에서 손을 천천히 움직인다 → 진세 패널만 반응. 이어서 **혜연**, **연우** 차례로. 각 사람이 자기 센서 앞에 있고 허브에서 이름이 반응하는 것이 한 화면에 보이게 한다.
3. 세 사람이 동시에 가까이 대본다 → "동시 접근" 배너와 랭킹.
4. (선택) 한 사람이 센서를 가리거나 앱을 끄면 그 패널이 `응답 없음`으로 바뀌고, 다시 켜면 자동 복구되는 것을 보인다.
5. (선택) 레이더 보기에서 사람이 걸어가는 장면, 3D 포인트 클라우드 보기.

**주의**
- 화면 반응이 실제 움직임보다 **약 0.4초 늦다** (공용 브로커 경유 + 센서 측정 주기). 프레임 단위로 맞추려 하지 말고, 1초 이상 이어지는 동작으로 보여 준다.
- 허브는 본인 노트북에서만 열면 세 보드의 데이터를 모두 구독해서 보여 준다. 팀원 화면을 각자 녹화하지 않아도 된다.
